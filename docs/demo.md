# Демонстрация HookRelay

## Сценарий на несколько минут

1. Задайте POSTGRES_PASSWORD в `.env`, запустите `docker compose --profile demo --profile monitoring up -d --build --wait`.
2. Откройте localhost:8080. Создайте endpoint с URL `http://receiver:9000/webhook` и секретом dev-secret (либо вашим WEBHOOK_SECRET).
3. Отправьте событие order.created с payload `{"order_id":42}`. Дождитесь delivered и откройте попытки: ожидаются одна запись и HTTP 204.
4. Создайте другой endpoint с тем же URL и неверным секретом. Событие станет failed с HTTP 401 без автоматических повторов.
5. Нажмите «Повторить» у failed: номер попытки увеличится, ID и предыдущая история останутся. При прежнем неверном секрете результат снова будет 401.
6. Перезапустите app через `docker compose restart app`. Endpoints, события и история останутся в панели.
7. На localhost:9090 выполните `hookrelay_queue_events` и `hookrelay_delivery_attempts_total`. Логи доступны через `docker compose logs --tail 30 app`.

Секрет в форме и конфигурации получателя должен совпадать. В примере получателя нет бизнес-обработки и защиты от повторного выполнения.

## Небольшая нагрузка

```powershell
docker compose exec app /app/loadgen -endpoint-url http://receiver:9000/webhook -secret dev-secret -count 100 -concurrency 4 -timeout 30s
```

Либо из Go, если приложение и получатель доступны по указанным адресам:

```powershell
go run ./cmd/loadgen -base-url http://localhost:8080 -endpoint-url http://127.0.0.1:9000/webhook -secret dev-secret -count 100 -concurrency 4
```

endpoint-url задаётся с точки зрения сервера HookRelay, base-url - с точки зрения генератора. Параллелизм генератора управляет входящими POST, а не количеством воркеров сервиса.

Генератор создаёт отдельный endpoint и до 10000 событий типа load.test. Число входящих запросов ограничено concurrency (1–64). Общий timeout по умолчанию 30 секунд, каждый HTTP-запрос ограничен пятью секундами. В течение общего срока генератор опрашивает список событий и учитывает только полученные им ID.

Вывод JSON: accepted, rejected, delivered, failed, unfinished, seconds. Accepted означает подтверждённый API приём, а не гарантированную доставку. Rejected включает HTTP-ошибки и запросы без подтверждённого ответа: при потере ответа сервер мог успеть сохранить событие. Наличие rejected/failed или истечение ожидания приводит к ненулевому коду выхода. Незавершённые события остаются в очереди и не отменяются.

Данные генератора остаются в БД. Запускайте его на отдельном демонстрационном экземпляре, если рабочую историю нельзя засорять. Чтение списков без пагинации и маленький объём проверки не позволяют считать этот инструмент полноценным бенчмарком. Не переносите показатели своего компьютера в обещание производительности сервиса.

## Рассказ о проекте

«HookRelay принимает webhook-события через REST API и доставляет их в фоне. PostgreSQL хранит и сами события, и очередь. Два воркера забирают готовые задания через SKIP LOCKED, отправляют подписанный JSON и одной транзакцией сохраняют историю и результат. Для временных ошибок есть три повтора, для ручного разбора - панель, JSON-логи и Prometheus. После аварии аренда позволяет продолжить обработку. Повторная отправка возможна, поэтому exactly-once я не обещаю».

Для описания в резюме можно использовать: «Сервис доставки webhook на Go: REST API, PostgreSQL, конкурентные воркеры, аренды заданий, повторы, HMAC-SHA256, веб-панель, Prometheus, Docker Compose и интеграционные тесты».

Подготовьтесь объяснить, где заканчивается транзакция захвата, зачем версия аренды, что происходит при 500 и timeout, почему 401 не повторяется автоматически и почему успешный POST всё равно может быть отправлен повторно. Подробности - в [решениях](decisions.md) и [архитектуре](architecture.md).

# Подпись webhook

Каждый исходящий webhook содержит подпись HMAC-SHA256. Ключ — значение `secret` соответствующего endpoint. Подписываются точные байты HTTP-тела, содержащего `event.Payload`. ID и другие заголовки в расчёт не входят.

## Формат запроса

```http
POST /webhook HTTP/1.1
Content-Type: application/json
X-HookRelay-Event-ID: <event-id>
X-HookRelay-Signature: sha256=<64 шестнадцатеричных символа>

{"order_id":42}
```

Алгоритм:

```text
digest = HMAC-SHA256(key = UTF-8(secret), message = raw HTTP body)
header = "sha256=" + lowercase_hex(digest)
```

Секрет используется как строка без декодирования из hex/base64 и без удаления пробелов. Отправитель отклоняет пустой или состоящий из пробелов секрет до HTTP-отправки. API уже проверяет обязательность этого поля при создании endpoint. В заголовках передаются ID и подпись; сам секрет не передаётся.

Подпись вычисляется заново при каждой отправке, включая автоматические и ручные повторы. При неизменных теле и секрете результат одинаковый.

## Проверка у получателя

1. Прочитать исходное тело запроса как байты с ограничением размера.
2. Получить единственный `X-HookRelay-Signature` и проверить префикс `sha256=`.
3. Декодировать следующие 64 hex-символа в 32 байта.
4. Вычислить HMAC-SHA256 над прочитанным телом с тем же секретом.
5. Сравнить полученные байты через `hmac.Equal`.
6. Выполнять действие получателя только после успешной проверки.

`hmac.Equal` предназначен для сравнения MAC без раскрытия информации о совпадении через время сравнения. См. [документацию Go](https://pkg.go.dev/crypto/hmac).

Не нужно сначала разбирать JSON и сериализовать его обратно: пробелы, переносы и порядок ключей влияют на подпись. PostgreSQL хранит payload как JSONB и может изменить форматирование по сравнению с входным API-запросом. Проверять нужно именно полученное HTTP-тело.

В репозитории проверка находится в `internal/signature.Verify`, рабочий пример HTTP-обработчика — в `examples/receiver/handler.go`, а запуск примера — в `examples/receiver/main.go`.

## Запуск примера

В отдельном PowerShell:

```powershell
$env:WEBHOOK_SECRET = "dev-secret"
go run ./examples/receiver
```

В HookRelay создайте endpoint с URL `http://127.0.0.1:9000/webhook` и `secret: "dev-secret"`, затем отправьте событие через API. Полный сценарий создания находится в [HTTP API](api.md).

Пример слушает только `127.0.0.1:9000`. Его переменная окружения задаётся в том же терминале, где он запускается. Go автоматически не загружает `.env`. При отсутствии или пустом `WEBHOOK_SECRET` процесс завершается до запуска HTTP-сервера.

Ответы получателя:

| Код | Причина |
| --- | --- |
| `204` | Подпись верна, пример принял событие |
| `401` | Подпись отсутствует, неверна, повреждена или заголовок повторён |
| `400` | Не удалось прочитать тело |
| `413` | Тело больше 1 MiB |

При `401` HookRelay сохраняет неуспешную попытку и переводит событие в `failed`: этот код не относится к временным ошибкам. Пример не выводит секрет или тело в лог; после проверки он выводит ID из заголовка.

Неподписанный запрос для проверки отказа:

```powershell
curl.exe -i -X POST http://127.0.0.1:9000/webhook -H "Content-Type: application/json" --data-binary '{}'
```

Ожидается `401 Unauthorized`.

## Границы защиты

HMAC подтверждает целостность тела и знание общего секрета. Любой владелец секрета может создать такую подпись, включая самого получателя. Это не шифрование и не цифровая подпись с открытым ключом. Для конфиденциальности при передаче нужен HTTPS.

ID события не подписан. Его можно использовать как подсказку для обработки дублей, но HMAC тела не подтверждает подлинность этого заголовка. Протокол не содержит подписанной даты или срока действия: перехваченный запрос можно воспроизвести. Сам пример получателя не хранит полученные события и не устраняет дубли.

Секреты endpoints хранятся в PostgreSQL открытым текстом. API не возвращает их в ответах; пример `dev-secret` предназначен для локальной проверки. Для своего получателя задайте отдельный случайный секрет.

## Проверки

```powershell
go test ./internal/signature ./internal/delivery ./examples/receiver
$env:TEST_DATABASE_URL = $env:DATABASE_URL
go test -count=1 -race ./...
go vet ./...
```

Модуль подписи проверяется по независимому [контрольному примеру RFC 4231, раздел 4.2](https://www.rfc-editor.org/rfc/rfc4231.html#section-4.2). Тесты получателя проверяют неверный секрет, изменения тела и формат заголовка. Интеграционные тесты с PostgreSQL проверяют API → БД → воркер → проверяющий получатель, автоматический повтор, ручной повтор и историю `204`/`401`. Без `TEST_DATABASE_URL` тесты PostgreSQL пропускаются.

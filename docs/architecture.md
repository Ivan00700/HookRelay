# Архитектура HookRelay

HookRelay принимает webhook-события через HTTP API, сохраняет их в PostgreSQL и доставляет получателям двумя воркерами. Состояние очереди, расписание и история попыток находятся в БД.

## Структура

## Запуск

1. `main` создаёт контекст остановки по сигналам и передаёт его в `orchestrator.Run`.
2. Orchestrator открывает PostgreSQL по `DATABASE_URL`, выполняет Ping и проверяет поля очереди. На подключение и проверку отведено пять секунд.
3. Создаются `PostgresStore`, общий HTTP-клиент, Sender и pool из двух воркеров.
4. `httpapi.Handler` получает Store через конструктор и подключает маршруты к ServeMux. Dashboard подключает страницу и статические файлы к тому же серверу.
5. HTTP-сервер запускается на `HTTP_PORT`, по умолчанию `8080`.

HTTP-обработчики обращаются к Store через интерфейс. SQL-хранилище не зависит от HTTP. Delivery использует отдельный интерфейс DeliveryStore и получает адрес и секрет endpoint перед отправкой.

## Доставка события

1. Обработчик проверяет JSON и поля, назначает ID и сохраняет событие `pending`.
2. Воркер выбирает готовую строку через `FOR UPDATE SKIP LOCKED`. В короткой транзакции назначаются аренда на 30 секунд и новая версия, увеличиваются счётчики и создаётся попытка.
3. После COMMIT выполняется HTTP POST с исходным payload из БД. Таймаут запроса — три секунды. `X-HookRelay-Signature` содержит HMAC-SHA256 над отправляемыми байтами, `X-HookRelay-Event-ID` — ID события.
4. Ответ `2xx` даёт `delivered`. Сеть, timeout, `408`, `429` и `5xx` допускают повторы через 5 секунд, 30 секунд и 2 минуты. Остальные ошибки либо исчерпание четырёх попыток дают `failed`.
5. Результат попытки, статус события и дата следующей отправки записываются одной транзакцией с проверкой аренды. Старый владелец не может перезаписать результат нового.

При истечении аренды незавершённая попытка помечается прерванной. Каждый захват расходует попытку, в том числе перед аварией. Ручной повтор из `failed` обнуляет счётчик цикла, сохраняя ID и всю историю.

## Завершение

По сигналу HTTP-сервер получает до десяти секунд на завершение обработчиков. Затем pool прекращает новые захваты и ждёт начатые отправки через WaitGroup. После завершения воркеров закрывается пул соединений PostgreSQL. При аварии данные остаются в БД, а захваченное задание становится доступным после истечения аренды.

## Проверка

Быстрые тесты используют MemoryStore и httptest. Интеграционные тесты создают отдельные схемы PostgreSQL и применяют все миграции. Они проверяют CRUD, HTTP API, несколько воркеров, восстановление после аварии, историю, расписание, ручной повтор и подпись реальных запросов. Запуск и настройка TEST_DATABASE_URL описаны в [документации PostgreSQL](postgres.md).

Формат подписи и границы её защиты описаны в [документации webhook](webhook-signatures.md). Маршруты и примеры запросов находятся в [HTTP API](api.md), сценарии и команды проверок - в [тестировании](testing.md).

Панель работает поверх REST API через Fetch. В браузер не передаются SQL-подключение и секреты сохранённых endpoints. Её устройство и сценарии использования описаны в [документации панели](dashboard.md).

HTTP-сервер обёрнут в middleware наблюдаемости: request ID и логгер передаются через context, после обработки записываются статус и длительность. API и pool получают один Monitor процесса. Счётчики обновляются после сохранения события или результата попытки. Gauge очереди и статусов читаются из PostgreSQL при scrape. Registry создаётся отдельно для каждого запуска сервиса. Формат и ограничения описаны в [наблюдаемости](observability.md).

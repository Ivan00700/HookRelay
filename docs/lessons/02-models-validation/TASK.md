# Этап 2 — модели, JSON и валидация

Статус: в работе.

Этап состоит из двух самостоятельных частей:

1. **2A — модели и JSON**: структуры, пользовательские типы, константы, struct tags и `json.RawMessage`.
2. **2B — валидация и ошибки**: методы, разбор URL, проверка входных данных и собственная ошибка валидации.

Сейчас выполняется только часть 2A. К 2B переходим после ревью моделей.

## Зачем нужен этот этап

HTTP-сервер уже умеет принять запрос, но приложение пока не знает, что такое
endpoint и событие. Модели задают словарь предметной области: какие данные
существуют, какого они типа и как выглядят в JSON.

После этапа нужно уметь объяснить:

- чем структура отличается от JSON;
- зачем поля структуры экспортируются с заглавной буквы;
- как работают JSON-теги;
- зачем `Secret` скрывать через `json:"-"`;
- почему статус лучше представить отдельным типом, а не произвольной строкой;
- чем `json.RawMessage` отличается от `map[string]any`;
- почему успешный `url.Parse` ещё не означает, что URL подходит HookRelay.

## Что прочитать перед практикой

Не пытайтесь запомнить документацию полностью. Для каждого пункта найдите
ответ на указанные вопросы.

### 1. Структуры и методы

- [A Tour of Go: Structs](https://go.dev/tour/moretypes/2)
- локально: `go doc time.Time`

Нужно понять:

- как объявляется структура;
- что такое zero value;
- почему поля с маленькой буквы не видны другим пакетам;
- как обратиться к полю через точку;
- чем именованный тип отличается от type alias.

### 2. JSON

- [Документация encoding/json](https://pkg.go.dev/encoding/json)
- локально: `go doc encoding/json.Marshal`
- локально: `go doc encoding/json.Unmarshal`
- локально: `go doc encoding/json.RawMessage`
- локально: `go doc encoding/json.Valid`

Используем обычный пакет `encoding/json`, доступный в установленном Go 1.24.

Нужно понять:

- Marshal: Go-значение → JSON;
- Unmarshal: JSON → Go-значение;
- сериализуются только экспортируемые поля;
- тег `json:"endpoint_id"` меняет имя поля;
- тег `json:"-"` полностью скрывает поле;
- `RawMessage` хранит необработанный JSON.

### 3. Ошибки — обзор перед частью 2B

- [Error handling and Go](https://go.dev/blog/error-handling-and-go)

Пока достаточно понять:

- ошибка — обычное значение, реализующее интерфейс `error`;
- `nil` означает отсутствие ошибки;
- ошибку нужно вернуть вызывающему коду, а не скрывать.

### 4. URL — обзор перед частью 2B

- [Документация net/url](https://pkg.go.dev/net/url)
- локально: `go doc net/url.Parse`

Пока только посмотрите поля `Scheme` и `Host` у `url.URL`.

## Тренировка 2A

Для экспериментов используйте:

```text
.scratch/stage-02/main.go
```

Каталог `.scratch` игнорируется Git и не попадёт в проект.

### Упражнение 1 — структура и JSON-теги

Создайте временную структуру `Book` с полями:

| Поле Go | Тип | Поле JSON |
|---|---|---|
| `Title` | `string` | `title` |
| `Pages` | `int` | `pages` |
| `InternalNote` | `string` | не должно попадать в JSON |

Создайте значение, выполните `json.Marshal` и напечатайте результат.

Ожидайте JSON следующей формы:

```json
{"title":"The Go Programming Language","pages":380}
```

### Упражнение 2 — обратное преобразование

Возьмите JSON:

```json
{"title":"Learning Go","pages":375}
```

Преобразуйте его в `Book` через `json.Unmarshal` и выведите оба поля.
Обратите внимание, что в `Unmarshal` передаётся указатель.

### Упражнение 3 — произвольный payload

Создайте структуру с полем:

```go
Payload json.RawMessage
```

Поместите туда объект:

```json
{"order_id":42,"paid":true}
```

После `json.Marshal` payload должен остаться вложенным объектом, а не стать
строкой с экранированными кавычками.

Запуск тренировки:

```powershell
go run ./.scratch/stage-02
```

После того как принцип понятен, тренировочный файл можно оставить локально:
Git его не увидит.

## Задание 2A — модели проекта

Создайте пакет:

```text
internal/domain
```

В нём создайте два файла:

```text
internal/domain/endpoint.go
internal/domain/event.go
```

Не добавляйте пока HTTP-обработчики, генерацию ID, базу данных, конструкторы,
методы валидации или сторонние зависимости.

### Модель Endpoint

Объявите структуру `Endpoint`:

| Поле | Тип | JSON-тег | Назначение |
|---|---|---|---|
| `ID` | `string` | `id` | идентификатор |
| `Name` | `string` | `name` | понятное имя |
| `URL` | `string` | `url` | адрес получателя webhook |
| `Secret` | `string` | `-` | секрет HMAC, не выдаётся через API |
| `CreatedAt` | `time.Time` | `created_at` | время создания |

Также объявите `CreateEndpointInput`, содержащую только данные, которые
присылает пользователь:

- `Name string`;
- `URL string`;
- `Secret string`.

У всех трёх полей должны быть JSON-теги в snake_case.

Почему две структуры: клиент не должен задавать `ID` и `CreatedAt` —
в будущем их создаст само приложение.

### Статус доставки

Создайте именованный строковый тип:

```go
type DeliveryStatus string
```

И четыре типизированные константы со строковыми значениями:

- `pending`;
- `processing`;
- `delivered`;
- `failed`.

Имена Go-констант выберите так, чтобы из имени было понятно, что это статусы
доставки, и чтобы они не конфликтовали с будущими идентификаторами.

### Модель Event

Объявите структуру `Event`:

| Поле | Тип | JSON-тег |
|---|---|---|
| `ID` | `string` | `id` |
| `EndpointID` | `string` | `endpoint_id` |
| `Type` | `string` | `type` |
| `Payload` | `json.RawMessage` | `payload` |
| `Status` | `DeliveryStatus` | `status` |
| `CreatedAt` | `time.Time` | `created_at` |

Также объявите `CreateEventInput`:

- `EndpointID string`;
- `Type string`;
- `Payload json.RawMessage`.

Добавьте соответствующие JSON-теги.

## Самопроверка части 2A

Выполните:

```powershell
gofmt -w ./internal/domain
go vet ./...
go test ./...
git status --short
```

Проверьте себя:

- пакет называется `domain`, а не `main`;
- все необходимые поля экспортируются;
- секрет никогда не сериализуется;
- payload сериализуется как JSON-объект;
- для статуса нельзя случайно использовать обычный `int`;
- в `go.mod` не появились зависимости.

## Что пока не делать

- не подключать модели к `main.go`;
- не создавать endpoint HTTP API;
- не использовать UUID-библиотеку;
- не писать БД или repository;
- не добавлять методы `Validate` до ревью 2A;
- не копировать готовые модели из чужого проекта.

# Этап 2 — модели, JSON и валидация

Статус: в работе.

Этап состоит из двух самостоятельных частей:

1. **2A — модели и JSON**: структуры, пользовательские типы, константы, struct tags и `json.RawMessage`.
2. **2B — валидация и ошибки**: методы, разбор URL, проверка входных данных и собственная ошибка валидации.

Часть 2A завершена. Текущее задание — часть 2B в конце этого файла.

## Зачем нужен этот этап

HTTP-сервер уже умеет принять запрос, но приложение пока не знает, что такое
endpoint и событие. Модели задают словарь предметной области: какие данные
существуют, какого они типа и как выглядят в JSON.

После этапа нужно уметь объяснить:

- чем структура отличается от JSON;
- зачем поля структуры экспортируются с заглавной буквы;
- как работают JSON-теги;
- зачем `Secret` скрывать через `json:"-"`;
- почему статус лучше представить отдельным типом, а не произвольной строкой;
- чем `json.RawMessage` отличается от `map[string]any`;
- почему успешный `url.Parse` ещё не означает, что URL подходит HookRelay.

## Что прочитать перед практикой

Не пытайтесь запомнить документацию полностью. Для каждого пункта найдите
ответ на указанные вопросы.

### 1. Структуры и методы

- [A Tour of Go: Structs](https://go.dev/tour/moretypes/2)
- локально: `go doc time.Time`

Нужно понять:

- как объявляется структура;
- что такое zero value;
- почему поля с маленькой буквы не видны другим пакетам;
- как обратиться к полю через точку;
- чем именованный тип отличается от type alias.

### 2. JSON

- [Документация encoding/json](https://pkg.go.dev/encoding/json)
- локально: `go doc encoding/json.Marshal`
- локально: `go doc encoding/json.Unmarshal`
- локально: `go doc encoding/json.RawMessage`
- локально: `go doc encoding/json.Valid`

Используем обычный пакет `encoding/json`, доступный в установленном Go 1.24.

Нужно понять:

- Marshal: Go-значение → JSON;
- Unmarshal: JSON → Go-значение;
- сериализуются только экспортируемые поля;
- тег `json:"endpoint_id"` меняет имя поля;
- тег `json:"-"` полностью скрывает поле;
- `RawMessage` хранит необработанный JSON.

### 3. Ошибки — обзор перед частью 2B

- [Error handling and Go](https://go.dev/blog/error-handling-and-go)

Пока достаточно понять:

- ошибка — обычное значение, реализующее интерфейс `error`;
- `nil` означает отсутствие ошибки;
- ошибку нужно вернуть вызывающему коду, а не скрывать.

### 4. URL — обзор перед частью 2B

- [Документация net/url](https://pkg.go.dev/net/url)
- локально: `go doc net/url.Parse`

Пока только посмотрите поля `Scheme` и `Host` у `url.URL`.

### Модель Endpoint

Объявите структуру `Endpoint`:

| Поле | Тип | JSON-тег | Назначение |
|---|---|---|---|
| `ID` | `string` | `id` | идентификатор |
| `Name` | `string` | `name` | понятное имя |
| `URL` | `string` | `url` | адрес получателя webhook |
| `Secret` | `string` | `-` | секрет HMAC, не выдаётся через API |
| `CreatedAt` | `time.Time` | `created_at` | время создания |

Также объявите `CreateEndpointInput`, содержащую только данные, которые
присылает пользователь:

- `Name string`;
- `URL string`;
- `Secret string`.

У всех трёх полей должны быть JSON-теги в snake_case.

Почему две структуры: клиент не должен задавать `ID` и `CreatedAt` —
в будущем их создаст само приложение.

### Статус доставки

Создайте именованный строковый тип:

```go
type DeliveryStatus string
```

И четыре типизированные константы со строковыми значениями:

- `pending`;
- `processing`;
- `delivered`;
- `failed`.

Имена Go-констант выберите так, чтобы из имени было понятно, что это статусы
доставки, и чтобы они не конфликтовали с будущими идентификаторами.

### Модель Event

Также объявите `CreateEventInput`:

## Задание 2B — валидация и ошибки

### Цель

Модели описывают форму данных, но Go разрешает создать, например,
`CreateEndpointInput{URL: "not a URL"}`. Метод `Validate` должен сообщить
вызывающему коду, почему такое значение нельзя использовать.

За один подход реализуйте проверку двух входных структур, допустимость
статуса и понятную ошибку с именем проблемного поля. Пока это обычные методы
пакета `domain`: HTTP-обработчики и база данных здесь не нужны.

### Что прочитать и потренировать

1. [Методы в A Tour of Go](https://go.dev/tour/methods/1): на каком типе объявляется метод и как его вызвать.
2. [Ошибки в Go](https://go.dev/blog/error-handling-and-go): что означают `error` и `nil`, как вернуть ошибку вызывающему коду.
3. [Документация `url.Parse`](https://pkg.go.dev/net/url#Parse): посмотрите поля `Scheme`, `Host`, метод `Hostname()` и разницу между относительным и абсолютным URL.
4. [Документация `json.Valid`](https://pkg.go.dev/encoding/json#Valid): чем синтаксически корректный JSON отличается от JSON-объекта.
5. Локально выполните `go doc strings.TrimSpace`, `go doc net/url.Parse` и `go doc errors.As`.

В `.scratch/stage-02` попробуйте вывести результат `url.Parse` для четырёх
строк: `https://example.com/hook`, `example.com/hook`, `/hook` и
`ftp://example.com/hook`. Обратите внимание: отсутствие ошибки от `url.Parse`
ещё не означает, что URL подходит для доставки webhook.

### 1. Ошибка валидации

Создайте в `internal/domain/validation.go` тип `ValidationError` с двумя
экспортируемыми полями `Field string` и `Message string`. Реализуйте метод
`Error() string`, чтобы тип удовлетворял интерфейсу `error`. Формат строки:

```text
<field>: <message>
```

Например: `url: must be an absolute HTTP URL`. Точный текст сообщения для
каждого правила можете выбрать сами. Не включайте в ошибку значение секрета.
Каждый отказ методов `Validate` ниже должен возвращать `ValidationError`
(значением или указателем — выберите один вариант и используйте его везде).

### 2. Проверка CreateEndpointInput

Добавьте метод:

```go
func (in CreateEndpointInput) Validate() error
```

Проверяйте поля в порядке `Name`, `URL`, `Secret`; возвращайте **первую**
найденную ошибку. Если всё верно — `nil`. Метод только проверяет данные и не
меняет поля структуры.

| Поле ошибки | Правило |
|---|---|
| `name` | После `strings.TrimSpace` строка не должна быть пустой. |
| `url` | После `strings.TrimSpace` строка не должна быть пустой; `url.Parse` должен пройти без ошибки; схема — только `http` или `https`; `Hostname()` не должен быть пустым. |
| `secret` | После `strings.TrimSpace` строка не должна быть пустой. |

Для URL `http://localhost:8080/hook` и `https://example.com/hook` должны
проходить проверку. `example.com/hook`, `/hook`, `ftp://example.com/hook`
и `http:///hook` должны отклоняться. Пока не проверяйте доступность адреса
по сети и не запрещайте localhost: это отдельные темы следующих этапов.

### 3. Проверка CreateEventInput

Добавьте метод:

```go
func (in CreateEventInput) Validate() error
```

Порядок проверок: `EndpointID`, `Type`, `Payload`. Ошибка содержит имя поля
`endpoint_id`, `type` или `payload`. Правила:

- `EndpointID` и `Type` не должны состоять только из пробелов;
- `Payload` должен быть синтаксически корректным JSON;
- верхний уровень `Payload` должен быть **объектом**. `{}` допустим, а
  пустые байты, `null`, `[]` и `"text"` — нет.

Подсказка: сначала проверьте `json.Valid`, затем выясните тип верхнего уровня.
Помните о пробелах перед `{`.

### 4. Допустимые статусы

Добавьте метод на `DeliveryStatus`:

```go
func (s DeliveryStatus) Valid() bool
```

Он возвращает `true` для четырёх объявленных констант и `false` для любой
другой строки, включая пустую. Этот метод ничего не меняет и не возвращает
ошибку.

`hookrelay/internal/domain`, вызывает оба `Validate` и `Valid`, печатает
результаты. Проверьте минимум такие случаи:

| Данные | Ожидание |
|---|---|
| Endpoint с именем, HTTP URL и секретом | `nil` |

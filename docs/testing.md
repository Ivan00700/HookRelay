# Проверка HookRelay

Полный прогон проверяет API, правила доставки и реальное хранилище PostgreSQL. Для интерфейса есть HTTP-проверки встроенных файлов; автоматизации браузера в Go-тестах нет.

## Быстрый запуск

Нужны Go с поддержкой race detector и работающий PostgreSQL с правом создавать схемы. На Windows для `-race` нужен доступный C-компилятор, например GCC из MinGW-w64. Подключение базы описано в [PostgreSQL](postgres.md).

В PowerShell из корня репозитория:

```powershell
docker compose up -d --wait db
$databasePassword = [uri]::EscapeDataString('пароль из POSTGRES_PASSWORD')
$env:TEST_DATABASE_URL = "postgres://hookrelay:${databasePassword}@127.0.0.1:5433/hookrelay?sslmode=disable"
./scripts/check.ps1
```

При другом `POSTGRES_PORT` измените порт в URL. Если `DATABASE_URL` уже задана и пользователь имеет право создавать схемы, можно использовать `$env:TEST_DATABASE_URL = $env:DATABASE_URL`. Пароль не выводится скриптом. Go и скрипт не загружают `.env` автоматически.

Скрипт запускает из корня проекта:

```powershell
go test -count=1 -timeout=2m ./...
go test -count=1 -race -timeout=2m '-coverprofile=coverage.out' ./...
go vet ./...
go build ./...
```

При ошибке следующая команда не выполняется. `-count=1` отключает использование кэшированных результатов тестов. Лимит `2m` действует отдельно на тестовый бинарник каждого пакета. `coverage.out` не попадает в Git.

Без `TEST_DATABASE_URL` полный режим останавливается до запуска проверок, чтобы пропущенные интеграционные тесты не выглядели полным успешным прогоном. Неправильная или недоступная БД приводит к падению интеграционных тестов.

Для проверки без PostgreSQL:

```powershell
./scripts/check.ps1 -Unit
```

Этот режим временно убирает `TEST_DATABASE_URL` и восстанавливает её после проверки. Выполняются все доступные без БД тесты, включая HTTP, подписи и MemoryStore; интеграционные тесты явно пропускаются. Покрытие перезаписывается результатом последнего прогона.

## Требования и проверки

| Что проверяется | Где находятся тесты | Основные сценарии |
| --- | --- | --- |
| Валидация | `internal/domain/validation_test.go` | Пустые поля, HTTP(S) URL, некорректный JSON, объект вместо массива, строки или `null` |
| Статусы и повторы | `internal/domain/event_test.go`, `delivery_test.go` | Разрешённые переходы, четыре попытки, интервалы 5/30/120 секунд |
| HMAC | `internal/signature`, `examples/receiver` | Контрольный пример RFC 4231, изменение тела, неверный секрет, повреждённая и повторяющаяся подпись |
| HTTP API | `internal/httpapi` | CRUD, валидация, лимит тела, JSON-ошибки, история и ручной повтор |
| Хранилища | `internal/repository` | MemoryStore и PostgreSQL, ограничения, копирование данных, отмена context |
| Доставка | `internal/delivery/sender_test.go` | Тело и заголовки POST, ошибки, таймаут, запрет редиректов |
| Конкурентность | `internal/delivery/pool_test.go`, `pool_integration_test.go`, `internal/repository/queue_integration_test.go` | Лимит воркеров, два пула, конкурентный захват, пропуск блокировок, завершение активной отправки |
| Восстановление | `internal/delivery/pool_integration_test.go`, `recovery_integration_test.go` | Авария процесса во время HTTP, потеря записи успешного результата и повтор после аренды |
| История и расписание | `internal/repository/retry_integration_test.go`, `internal/delivery/retry_integration_test.go` | Атомарность истории и статуса, сохранение даты после переподключения, лимит при авариях и ручной повтор |
| Запуск приложения | `internal/orchestrator/orchestrator_integration_test.go` | Реальный HTTP-сервер, API → PostgreSQL → HTTP-получатель, остановка и повторный запуск |
| Наблюдаемость | `internal/observability`, `internal/httpapi/monitoring*_test.go` | Request ID, JSON-логи, метрики, ограниченные labels, `/ready` при отказе хранилища |
| Веб-панель | `internal/dashboard/handler_test.go`, тест запуска приложения | Страница, JS/CSS, маршруты, типы содержимого и защитные заголовки |

Проверки с реальным PostgreSQL используют `internal/testutil.Database`. Каждый вызов создаёт случайную схему `hookrelay_test_*`, применяет все SQL-миграции в транзакции и передаёт соединениям её `search_path`. После теста схема удаляется. Создавать таблицы вручную перед этим не требуется; таблицы приложения в `public` не используются.

## Проверка отказов

### Авария процесса

`TestQueueRecoversAfterProcessCrashIntegration` запускает отдельный тестовый процесс и принудительно завершает именно его во время исходящей отправки. Затем проверяет, что действующая аренда не перехватывается, а после её истечения другой воркер доставляет событие. Первая попытка остаётся в истории как прерванная.

### Ответ получателя получен, результат не записан

`TestPoolRecoversWhenSuccessfulDeliveryCannotBeSavedIntegration` проверяет более узкое окно отказа:

1. Получатель читает тело и проверяет HMAC и ID события.
2. До ответа `204` закрывается только пул соединений первого воркера. PostgreSQL и другие подключения продолжают работать.
3. Воркер получает успешный HTTP-ответ, но не может сохранить результат. Через независимое подключение проверяются `processing` и незавершённая попытка без HTTP-кода.
4. После истечения аренды новый пул повторяет доставку с тем же ID и корректной подписью.
5. В истории две попытки: прерванная и успешная; статус события — `delivered`.

Тест моделирует недоступность хранилища для воркера, а не выключение всего PostgreSQL. Он подтверждает возможность дубликатов после успешной обработки получателем: гарантия ровно одной обработки отсутствует.

### Длинные интервалы

Первая автоматическая повторная отправка в `TestPoolWaitsFiveSecondsBeforeRetryIntegration` действительно ждёт минимум пять секунд. Для интервалов 30/120 секунд тесты сначала проверяют сохранённую дату, затем сдвигают срок только своего задания. В тестах аварий аналогично сдвигается только тестовая аренда; отдельный тест проверяет естественное истечение короткой аренды.

Таким образом, полный прогон не ждёт несколько минут и не требует остановки общего контейнера или изменения рабочих событий.

## Отдельные сценарии и покрытие

При заданной `TEST_DATABASE_URL`:

```powershell
go test -count=1 -race ./internal/delivery -run 'TestQueueRecoversAfterProcessCrashIntegration|TestPoolRecoversWhenSuccessfulDeliveryCannotBeSavedIntegration' -v
go test -count=1 ./internal/domain -v
go tool cover '-func=coverage.out'
go tool cover '-html=coverage.out'
```

Процент покрытия помогает найти непроверенные ветки, но не доказывает правильность. Проверки сравнивают наблюдаемое поведение: HTTP-ответы, сохранённые статусы, даты, историю и число отправок. Race detector ищет гонки только в выполненных сценариях; ручную проверку веб-интерфейса он не заменяет.
